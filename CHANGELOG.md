### Added

**Diagnostic programs** (`programs/`) — standalone PacScript, each answering one
question, printing to the pendant message log, and read-only unless stated.

- `Chk01_RobotCalibration.pcs` — reports whether the server holds a kinematic
  calibration for this robot. Distinct from the camera hand-eye calibration, and
  invisible to programs that use no server IK.
- `Chk02_RigPoseIterate.pcs` — pushes a camera rig pose via `CamSetCalibrationRigPose`
  without launching a calibration sweep, turning a 5–10 minute iteration into seconds.
- `Chk03_ToolCompare.pcs` — compares the controller's tool definition against the one
  Cambrian holds, derived from `CamGetFlangeFK` versus `CamGetFK`.
- `Chk04_PickPathConsistency.pcs` — prints the two targets `CamExecutePath` and
  `CamExecutePathReverse` drive to, without moving the robot. Isolates the J6 wrist wind.
- `Cal01_AutoCalibration.pcs` — hand-eye calibration with `CamSetCalibrationMount` and
  `CamNewCalibration` set explicitly, plus acceptance criteria in the header.

### Fixed

- **J6 wrist rotation on the final linear grasp leg.** `CamGetPickPath` returns a grasp
  pose that is not forward-kinematics-consistent with the grasp joints it returns
  alongside it — unlike `CamGetIKEx`, which explicitly normalises its pose for exactly
  this reason. `CamExecutePath` drives `Move L, CamGraspPose` while
  `CamExecutePathReverse` drives `Move L, J2P( CamPathJoints( N ) )`, so the wrist wound
  180° into the grasp and unwound on the retract. Resolved in the calling program with
  `CamGraspPose = J2P( CamGraspJoints )` after a successful `CamGetPickPath`, leaving the
  vendor library untouched.

### Verified

Two PacScript semantics previously reasoned about from library usage, now cited from the
manual:

- `J2P` reflects the current work **and** tool coordinates, so it is not a flange pose
  and `J2P( CurJnt )` equals `CurPos`. This validates the fix above — it yields a TCP
  pose through the active tool, matching what `CamExecutePathReverse` targets.
- `DevH` applies its deviation in the reference pose's own coordinate system, which is
  what makes `CamOffsetPose( p, 0, 0, 20, 0, 0, 0 )` mean 20 mm along tool Z.

### Known issues

- **Transit-leg J6 rotation unresolved.** `Move P, CamPathJoints(N)` legs still wind
  180°. The server's grasp IK selects a wrist branch 180° from the pose it reports; the
  RRT then plans a continuous path to it. Not addressable from the robot program.
- **Grasp point Symmetry is `Cylindrical`** with a rotation axis apparently parallel to
  the gripper approach axis, making every variant a pure wrist spin. Outstanding test:
  Symmetry → None, reload the model, re-run `Chk04`.
- **Version skew.** `Cambrian_API.pcs` v1.6 declares it requires CamVISION 2.4.x; the
  cell runs 2.5.1. `CamInit` only checks for a server that is too old, so the mismatch
  passes silently.
- **TCP length unresolved.** `TOOL1` Z is 199.9489 with a 20 mm `PushIn`. Either the tool
  is ~20 mm long and `PushIn` compensates, or the tool is correct and `PushIn` is genuine
  cup preload. A direct measurement settles it.
- Three bugs identified in `Cambrian_API.pcs` v1.6 — see `CLAUDE.md`.
